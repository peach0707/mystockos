# iPhone Safari実機確認手順（PR #1・マージ前）

実機確認は未実施。PRのGitHubページはコード確認画面でありアプリの確認用URLではない。mainに未マージのため現在の本番URLにもこの変更は出ない。

## 準備

担当者が`feature/kabugorilla-v2-phase1`の最新コミットを、**本番と別originのHTTPS確認環境**に配信する。確認対象コミットを画面外のレビュー記録に残す。今回は確認用URLの新規発行・本番公開は行っていない。

配信はビルド不要で、index.html、assets、既存の公開JSONを同じ相対パスに置く。HTTPSを使い、Safariのsecure-context APIを利用可能にする。本番のGitHub Pages公開設定やmainを切り替えて確認しない。別originなら既存の個人台帳と分離できる。APIキーも実際の個人資産もテスト用環境へ入力しない。

確認URLを用意した後、iPhoneでそのURLをSafariから開く。テスト用の架空データだけを使う。バックアップ/移行試験を同じoriginで行う場合は、先に設定から元データを書き出す。

## タップして確認する順序

1. 下部のホーム/テーマ/銘柄/ニュース/保有と右上の歯車が押せること。最下行が固定ナビやホームバーに隠れないこと。縦横向き、キーボード表示時も保存ボタンまで到達できること。
2. 保有 → 日次評価。9/11（金）に50,000,000円、9/14（月）に51,000,000円を記録。評価基準は「実機テスト」。土日は入力しない。
3. 損益カレンダー → 9/14。総運用損益+1,000,000円、期間率+2%、比較期間9/11→9/14。9/12と9/13のマスは「—」で、0円/0%の運用日にならないこと。
4. 保有 → 入出金台帳。9/12に入金1,000,000円を登録。完全性を「完全」にする。9/14の運用損益が0円、純入金1,000,000円、率は未算出になること。入出金の編集/削除でも再計算されること。
5. 別の記録で9/4→9/8の比較を作り、間の9/7を評価しなくても計算できること。休場日を自動的に0円の運用日として作らないこと。
6. 前年12/31に40,000,000円の基準評価を記録。毎日は埋めない。年初来画面で最新資産との差と期間中の純入金控除が合うこと。前年最終営業日の評価を明示基準に指定する場合も基準日が表示されること。
7. 入出金台帳の完全性を「不完全」に変更。運用損益はデータ不足になること。完全へ戻すと復帰すること。年初基準のない状態でも年初来を捏造しないこと。
8. 配当内訳で9/12にMU、税引後10USD、FX150、参考税額3USDを登録。9/12は資産評価がなくても実入金1,500円を表示すること。9/14では比較期間の配当として照合されるが、総資産と総運用損益が台帳登録だけで増えないこと。税額も再控除されないこと。
9. 日付詳細に総損益、率、株価/為替/配当/実現/その他、未分類差額、銘柄/テーマ寄与があること。要因未入力は「未分類」。100万円の損益に要因未入力なら100万円は未分類差額に残ること。
10. 設定 → JSON書き出し、読み込み。iPhoneの保存操作ができること。評価CSV/入出金CSVのテンプレートから読込を確認。同じ入出金IDを2回読んでも増えないこと。不正データは保存前に拒否すること。
11. Safariのタブを閉じて開き直して、同じoriginの台帳が残ること。別originに個人台帳が送られないこと。旧v2移行は元キー保持・v3作成・完全性確認メッセージを確認する。
12. テーマのranked/thin/heat_only/観察、Turning/Weakening、VIXの独立基準日が以前どおりで、Forwardの買い/売り判断や架空の勝率がないこと。

記録するもの：iPhone機種、iOS/Safari版、確認URLとコミット、成功/失敗の手順番号、スクリーンショット。実データを入れず、テスト後は確認用originのデータだけを整理する。本番originの保存データを消さない。
